  diagnosis was WRONG. The watchdog (llama_runner.py:1255) measures device-wide

  88 MB allowance — DWM fluctuation alone can blow that.
- Task failures (0/5) are real but caused by per-turn client timeouts at 3.5 t/s prefill
  (`turn N request failed: timed out`), not model death.
- Model-side truth: fits at 64k (~7.7-7.9 GB vs <physical-limit> MiB) with desktop kept lean;
  device-wide watchdog will false-kill at any tight ceiling when desktop VRAM fluctuates.

## Instrumented revalidation + per-process VRAM truth (15:43–, run `val-iq1s-2`)

Rerun at ceiling <physical-limit> (keepout 0) with a side probe (2 s CSV: `nvidia-smi --query-gpu` +
compute-apps) → `<user-profile>/Temp/vram-probe-iq1s.csv`. Issue #72 filed
with the full evidence chain.

- Device-wide idle baseline ~910 MB (desktop/WDDM); model load: 910 → 7853 MB stable.
- **Windows GPU Process Memory counters (PID 1113980): llama-server holds Dedicated
  7145.9 MB + Shared 586.0 MB = 7732 MB.** The model does NOT fully fit at 64k — 586 MB of
  model memory is demoted to system RAM (WDDM). The "shared = desktop only" hypothesis was
  wrong; Task Manager's 7.7 GB was the model's combined footprint.
- Bench 28.2 t/s and agentic scores therefore measure "Q1_S with 586 MB spilling". Unknown
  haircut vs hypothetical pure-VRAM 64k (impossible on 8.19 GB with this KV).
- Additional calibration fact: `nvidia-smi --query-gpu=memory.used` (7853) vs harness
  ctypes `nvmlDeviceGetMemoryInfo.used` (8038–8108 on same workload) disagree by ~250 MB —
  WDDM reserve accounting differs between the two "device-wide" paths; the watchdog uses
  the higher one.
- Operator decision consequence: since spill is already accepted at Q1, a higher quant
  (e.g. IQ2_XXS 7.3 GB, ~1.3–1.5 GB shared) trades more spill for a full bit of weight
  precision — candidate follow-up fingerprint. Alternatively 48k ctx fits fully dedicated
  (no shared) for a clean pure-VRAM comparison.
